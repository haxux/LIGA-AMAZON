# Exploration — Fase 1: Andamiaje (Docker + Laravel 13 + Filament v5)

## Current state

Greenfield repo. Only `ARQUITECTURA.md`, `.atl/` and `openspec/` exist. No `.git`, no
`composer.json`/`artisan`, no `docker-compose.yml`, no `docker/`.

`ARQUITECTURA.md` §6 already sketches a 3-service `docker-compose.yml` (`app` = custom
PHP 8.3-fpm Dockerfile, `web` = `nginx:alpine`, `db` = `mysql:8.0`) and a 5-step boot
sequence: `docker compose up -d --build` → `composer install` → `key:generate` →
`migrate --seed` → open `/` and `/admin`. That sequence silently assumes Laravel already
exists in the repo before `docker compose up` runs — it never says how `composer.json`/
`artisan` get created in the first place. **That's the chicken-and-egg gap this change
must resolve.**

`openspec/config.yaml` also already commits to `verify.build_command: "npm run build"`,
but the ARQUITECTURA docker-compose sketch has no Node/npm service — a second gap.

## Affected areas (files to be created — none exist yet)

- `docker-compose.yml` — root orchestration (app/web/db), per ARQUITECTURA §6
- `docker/php/Dockerfile` — PHP-FPM 8.3 image with extensions + Composer binary
- `docker/nginx/default.conf` — front-controller config routing to `public/index.php`
- `composer.json`, `artisan`, `public/index.php`, `bootstrap/`, `app/` — generated by the
  Laravel installer, not hand-written
- `.env` / `.env.example` — DB_HOST/DB_DATABASE/DB_USERNAME/DB_PASSWORD must match the
  `db` service env vars in `docker-compose.yml`
- `.gitignore`, `.gitattributes` (needed, currently absent) — per ARQUITECTURA §5/§7
- `app/Providers/Filament/AdminPanelProvider.php` — generated by `filament:install --panels`

## Approaches to the bootstrap (chicken-and-egg) problem

1. **Ephemeral Composer container scaffolds code once, then `docker compose up` runs it.**
   `docker run --rm -v ${PWD}:/app -w /app composer:2 composer create-project laravel/laravel . "^13.0"`
   before `docker compose up -d --build`. `docker/php/Dockerfile` stays a pure runtime
   image (PHP-FPM + extensions + Composer binary), never generates code itself.
   - Pros: matches ARQUITECTURA §6's documented boot sequence almost verbatim; small,
     cacheable, easy-to-audit Dockerfile; standard/widely documented pattern.
   - Cons: one manual one-off command not encoded inside `docker-compose.yml` itself;
     needs a throwaway image pull.
   - Effort: Low

2. **Self-bootstrapping `app` service entrypoint.** `entrypoint.sh` checks
   `if [ ! -f artisan ]; then composer create-project ...; fi` on every container start.
   - Pros: `docker compose up -d --build` alone is sufficient, nothing manual.
   - Cons: conflates "build once" vs "run every time"; must be carefully idempotent; adds
     entrypoint script complexity; CRLF risk on Windows-authored shell scripts; not what
     ARQUITECTURA §6 currently describes.
   - Effort: Medium

3. **Replace the custom docker-compose with Laravel Sail.**
   - Pros: battle-tested, less hand-maintained Nginx/Dockerfile config.
   - Cons: contradicts the already-approved ARQUITECTURA §5/§6 (explicit `docker/nginx` +
     `docker/php` custom layout, not Sail's artisan-managed compose file); Sail's default
     server isn't Nginx+PHP-FPM unless customized; would require reopening Fase 0 decisions.
   - Effort: Medium (mostly reconciling with existing docs)

**Recommendation: Approach 1.** Reproduces ARQUITECTURA §6's boot sequence exactly
(scaffold → compose up → install → migrate), keeps `docker/php/Dockerfile` single-purpose,
requires no revision to the already-approved architecture document.

## Additional technical findings (verified via web search — Laravel 13 / Filament v5 are
past training cutoff)

- **Laravel 13** requires PHP 8.3 minimum (8.1/8.2 dropped) — matches ARQUITECTURA's
  PHP 8.3+/8.4 target.
- **Filament v5** requires PHP ^8.2, Livewire ^4.1, `illuminate/contracts ^11.28|^12.0|^13.0`
  — compatible with Laravel 13. Livewire is pulled automatically as a Filament composer
  dependency, no manual install step needed.
- **PHP extensions** needed beyond the php-fpm base: `pdo_mysql`, `bcmath`, `gd` (or
  `imagick`), `zip`, `intl`, `exif`, `opcache`, `pcntl`. `mbstring/ctype/tokenizer/xml/dom/
  fileinfo/curl/openssl` are typically already present in official `php:8.3-fpm` builds.
- **Nginx `default.conf`** needs the standard Laravel front-controller pattern:
  `root /var/www/html/public;`, `try_files $uri $uri/ /index.php?$query_string;`,
  `location ~ \.php$ { fastcgi_pass app:9000; ... }` (hostname must match the `app`
  service name), plus a `deny all` rule for dotfiles to prevent `.env` exposure.
- **Filament install ordering** — missing from ARQUITECTURA §6 entirely. Correct sequence:
  `migrate --seed` (creates `users` table) → `composer require filament/filament:"^5.0"` →
  `php artisan filament:install --panels` → `php artisan make:filament-user`.

## Risks

- **Windows bind-mount I/O performance**: repo lives on NTFS, not native WSL2 filesystem.
  Docker Desktop's WSL2 backend bind-mounts NTFS through a slower 9p-style protocol —
  `composer install`, Vite watch, `artisan` file-cache ops can be noticeably slower.
  Acceptable for demo scope; future lever if painful: move repo under `\\wsl$\...`.
- **UID/permission mismatch**: if the one-off Composer container (Approach 1) and the
  long-running `app` service run as different users, files created by
  `composer create-project` may not be writable by php-fpm for `storage/` and
  `bootstrap/cache/`. Needs a consistent UID between scaffold step and Dockerfile `USER`.
- **CRLF line endings**: no `.gitattributes` yet; any `.sh` files authored/edited on
  Windows risk CRLF breaking `sh script.sh` inside the Linux container. Needs
  `.gitattributes` with `eol=lf` before any shell scripts land, and before `git init`.
- **Host port collisions**: ARQUITECTURA's sketch exposes MySQL on host `3306:3306`; if
  Windows host already runs local MySQL/XAMPP/WAMP the bind will fail. Recommend a
  non-default host port (e.g. `33060:3306`) or dropping the host port publish — `app`
  reaches `db` over the internal Docker network regardless.
- **Node/Vite build gap**: `openspec/config.yaml` declares `verify.build_command:
  "npm run build"`, but ARQUITECTURA §6's docker-compose sketch has no Node/npm service
  or host-Node assumption documented. Proposal must explicitly decide: host-installed
  Node, or an added `node` build stage/service.
- **Nested git-init risk**: Laravel's installer/`composer create-project` may initialize
  its own `.git` inside the `laravel/laravel` skeleton when writing into an existing
  non-git directory. Since this repo has no `.git` yet, sequencing (`git init` before or
  after scaffold) needs to be explicit to avoid an accidental nested repo.
